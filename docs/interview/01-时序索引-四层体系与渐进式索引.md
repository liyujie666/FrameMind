# 面试文档一：时序索引——Video → Event/Clip → Shot → Frame 四层体系

> 对应简历条目：**"将视频建模为多模态时序数据，设计 Video → Event/Clip → Shot → Frame 四层索引体系，支持视频摘要、事件检索、镜头理解和帧级定位，解决单帧索引无法表达动作变化与事件顺序的问题。"**
>
> 涉及代码：`src/service/agent/video_indexer.cpp/.h`、`src/service/agent/frame_extractor.cpp/.h`、`src/service/scene_detector.cpp/.h`、`src/model/video_representation.h`、`src/model/scene.h`

---

## 一、30 秒电梯话术（背熟）

> 视频是时序信号，不是图片集合。只存"场景首帧"等于把几十秒的视频有损压缩成一张静态图，"后来发生了什么""谁进入画面""字幕什么时候变"这类问题在索引阶段信息就不可逆丢失了。所以我把视频组织成分层索引：全局层做摘要、事件层做 5~30 秒语义片段、场景（Shot）层做镜头切分并保留首/中/尾多张代表帧、帧层做精确定位。索引用 L0/L1/L2 三级渐进构建——L0 秒级出场景骨架，L1 后台算 embedding 和转写，L2 按需调 VLM 深化，用户不用等全量分析完就能开始提问。取帧层我重写了独立的 FFmpeg FrameExtractor，一个视频只开一次解码器、单次顺序解码，替代了原来每帧都要重开文件、落盘临时 JPEG 再读回的播放器截帧链路。

## 二、理论基础（面试官问"为什么"时的弹药）

### 2.1 视频的数学建模

视频是多模态时序信号：

```
V = {(f_t, a_t, o_t)}, t = 1..T
```

- `f_t`：时刻 t 的画面（视觉）
- `a_t`：时刻 t 的音频/ASR 结果
- `o_t`：时刻 t 的 OCR、字幕等观测

**推论**：单帧只覆盖 `f_t0`，无法表达：
- 动作：需要比较 `f_t1 → f_t2`
- 进入/离开画面：依赖时间变化
- 屏幕文字变化：依赖多个时刻
- 场景内事件顺序：依赖时间序列

### 2.2 核心原则：数据粒度必须和问题粒度匹配

| 用户问题 | 合适的索引粒度 |
|---|---|
| "视频主要讲什么？" | Video 层（全局摘要） |
| "这一段发生了什么？" | Event/Clip 层（5~30s 语义片段） |
| "镜头什么时候切换？" | Shot 层（物理镜头边界） |
| "画面右边有几个人？招牌写了什么？" | Frame 层（精确定位/OCR/grounding） |
| "某人一共出现几次？" | Entity timeline（实体时间线） |

**面试金句**：如果只有"场景"和"全视频摘要"两层，系统无法稳定处理中等时间尺度的问题。一个 30 秒的长镜头里可能有"人进门 → 坐下 → 拿起杯子"三个事件，单一 Scene 表达不了它们。

### 2.3 分层的本质：分层检索

`Video ⊃ Event/Clip ⊃ Shot ⊃ Frame` 是一个分层索引：**粗粒度先召回，细粒度再局部验证**。好处：
- 不需要对全视频逐帧问大模型（成本可控）；
- 不会因只保留一帧失去时序信息（信息不丢）。

### 2.4 为什么不固定时长切分（每 10s 一段）

- 固定切分会把一个语义事件腰斩成两个 chunk（检索命中一半），也可能让一个静止画面占满一个 chunk（浪费）；
- 边界应来自内容本身：镜头检测、ASR 语义分段；
- 本项目 chunk 切分策略：**场景驱动为主、语音句子级为辅**。

## 三、架构设计

### 3.1 三层视频表示（`VideoRepresentation`）

```
语义层 Semantic  → videoSummary / sceneDescriptions / EventChain / EntityProfiles
结构层 Structural → scenes / speechSegments / entityRegistry / temporalIndex
感知层 Perceptual → 代表帧 / CLIP embedding / 音频
```

设计原则：**Agent 日常工作在语义层和结构层，仅在必要时下探到感知层**（取原始帧分析）。

### 3.2 渐进式三级索引（不让用户等）

```
视频打开
 ├─[Level 0] 即时（< 1~2s）
 │   ├─ 元信息：时长/分辨率/FPS/编码（从播放器或 FFmpeg 读）
 │   └─ 场景分割：直方图差异（默认）或 TransNetV2（深度模型）
 │   → 此时可回答"视频多长？有几个场景？"
 │
 ├─[Level 1] 后台异步（秒级~十秒级）
 │   ├─ 代表帧提取（每场景首/中/尾 ≤3 帧）
 │   ├─ CLIP 视觉 embedding（批量 ONNX 推理）
 │   ├─ Whisper 转写 → 语义分段
 │   └─ BGE 文本 embedding → 全部写入 VideoRAGStore
 │   → 此时可回答"帮我找到有 XX 的画面"（语义检索可用）
 │
 └─[Level 2] 按需深化（用户提问或检索命中时触发）
     ├─ VLM 场景描述（多帧 + 同期 ASR）
     ├─ 音视频融合（语义门控）
     └─ 全视频摘要生成
     → 此时可回答"这一段发生了什么"
```

**为什么按需**：全量 L2 是 VLM 调用 × 场景数，大部分场景用户根本不会问到，按需触发把成本花在刀刃上。

### 3.3 索引的产物：带元数据的 Chunk（`VideoChunk`）

每个 chunk 是检索单元，携带完整时间定位和元数据：

```cpp
// src/model/retrieval_result.h（简化）
struct VideoChunk {
    QString  chunkId;
    QString  videoId;
    int64_t  startMs, endMs;          // 时间区间——每个 chunk 必须有
    ChunkType chunkType;              // SceneSummary/SceneAudio/SpeechSegment/SceneFused/Event...
    QString  textContent;             // 文本化表示（文本检索路径）
    std::vector<float> textEmbedding; // BGE 向量
    std::vector<float> frameEmbedding;// CLIP 向量（帧级 chunk 有）
    QString  keyframePath;            // 代表帧缩略图路径
    QVariantMap metadata;             // scene_id / evidence_type / embedding_model_id...
};
```

这就是"四层粒度"在数据结构上的落地：不同 chunkType 对应不同层次的语义单元。

## 四、代码实现详解

### 4.1 主入口与缓存命中（`VideoIndexer::startIndex`）

```cpp
// 1) videoId = SHA1(文件大小 + 前 1MB 内容)
const QString videoId = computeVideoId(videoPath);

// 2) 已有 Level1 以上的缓存 → 直接复用，秒级完成
if (it.value()->level >= VideoRepresentation::Level1) {
    emit progress(100, StageDone, tr("索引完成 (缓存命中)"));
    emit indexCompleted(cached);
    return;
}

// 3) 无缓存 → invalidate 旧索引，起后台任务
if (m_ragStore) m_ragStore->invalidateVideo(videoId);
m_pool.start([...](){ buildLevel0(...); buildLevel1(...); });
```

**videoId 设计要点**（面试常问）：
- 不用全量 hash：大视频全量读太慢；
- `SHA1(文件大小 + 前 1MB)`：实践中足以区分"重新编辑过的文件"；
- 文件变了 → hash 变 → `invalidateVideo` 全量重建（索引生命周期管理）。

### 4.2 L0：采样策略与场景分割

**采样密度自动选择**（`video_indexer.cpp` 匿名空间）：

```cpp
// TransNetV2 模式：每秒 1 帧密集采样；回退模式（无模型）：每 10s 一帧
constexpr int kDenseFps           = 1;
constexpr int kSparseSamplePerSec = 10;
constexpr int kMaxDenseSample     = 600;   // 密集采样上限（10min 视频）
constexpr int kMaxSparseSample    = 200;

const bool useTransNet = m_sceneDet && m_sceneDet->isUsingTransNet();
const int sampleCount = computeSampleCount(repr->metadata.durationMs, useTransNet);
```

**场景分割双算法**（`scene_detector.cpp`）：
- **直方图差异（默认兜底）**：两帧降采样到 64×64 → RGB 颜色直方图 → **Bhattacharyya 距离** > 阈值 → 切换。1 分钟视频 120 帧比较 < 50ms，纯 Qt 实现。
- **TransNetV2（可选升级）**：ONNX 深度模型，输入 `[1,100,27,48,3]`，需要 1fps 密集采样。
- **自动降级**：`detectScenes` 里检测平均帧间隔 >2s 视为稀疏采样，**强制走直方图**（TransNetV2 对稀疏帧不适用）；模型加载失败保持直方图模式。

```cpp
// 场景边界判定主循环（简化）
for (int i = 0; i + 1 < frames.size(); ++i) {
    float score = probs.empty() ? histogramDifference(frames[i+1], frames[i])
                                : probs[i];          // TransNetV2 逐帧切换概率
    if (score > m_threshold) {
        Scene s; s.id = currentSceneId++;
        s.startMs = timestampsMs[sceneStartIdx];
        s.endMs   = timestampsMs[i + 1];
        s.keyframeMs = timestampsMs[sceneStartIdx]; // keyframe 取场景首帧
        scenes.append(s);
        sceneStartIdx = i + 1;
    }
}
```

### 4.3 多代表帧：从"场景首帧"到"首/中/尾三帧"

```cpp
// assignRepresentativeFrames()——核心改进
constexpr int kMaxFramesPerScene = 3;
const QVector<int> selected = {
    candidates.first(),                 // 首帧：场景开始状态
    candidates.at(candidates.size()/2), // 中间帧：过程状态
    candidates.last()                   // 尾帧：结束状态
};
```

**为什么是首/中/尾**：成本最低的时序覆盖——能表达"开始什么样、过程什么样、结束什么样"，直接支撑"状态变化"类问题。这是从"每个 Scene 的 keyframe 固定取 sceneStartIdx"（旧实现）演进来的。

**代表帧持久化**：落盘到 `AppData/keyframes/<videoId>/`，检索命中时按需加载缩略图（`keyframeThumb`），内存不常驻大图；索引缓存命中时秒级复用。

### 4.4 FrameExtractor：从零实现的批量取帧（本模块最重要的代码）

**旧链路的问题**（为什么必须重写）：

```
每次抽一帧：打开文件 → 初始化解码器 → seek → 解码
           → 写临时 JPEG → 读回 → 删除临时文件
```

抽几百帧时 I/O + 解码器初始化开销完全不可接受，且索引服务反向依赖了播放器 SDK（`SmartPlayer::extractThumbnail`），违反了"索引与播放器状态完全隔离"的原则。

**新实现**（`frame_extractor.cpp`）：

```cpp
QVector<Frame> FrameExtractor::extract(videoPath, requestedMs, options,
                                       cancelled, errorMessage)
{
    // 1) 目标时间戳排序 + 去重（保证单次顺序解码可消费）
    QVector<int64_t> targets = requestedMs;
    std::sort(targets.begin(), targets.end());
    targets.erase(std::unique(...), targets.end());

    // 2) 打开一次解码器（avformat_open_input + avcodec_open2）
    //    注册 interrupt_callback —— 取消标志可打断阻塞 I/O
    formatRaw->interrupt_callback.callback = &interruptIo;
    formatRaw->interrupt_callback.opaque = cancelled;

    // 3) sws_getContext 预建缩放器：解码格式 → RGB24，直接缩放到 maxEdge
    //    不走 JPEG 临时文件
    std::unique_ptr<SwsContext, SwsContextDeleter> scaler(sws_getContext(
        sourceWidth, sourceHeight, codecContext->pix_fmt,
        targetWidth, targetHeight, AV_PIX_FMT_RGB24, SWS_BILINEAR, ...));

    // 4) 单次顺序解码，解码到某 PTS 就消费所有 ≤PTS 的目标帧
    const auto consumeFrame = [&]() {
        const int64_t ptsMs = av_rescale_q(
            decoded->best_effort_timestamp - streamStart,
            stream->time_base, AVRational{1, 1000});
        while (targetIndex < targets.size() && ptsMs >= targets.at(targetIndex)) {
            sws_scale(...);                      // 解码帧 → RGB
            frame.ptsMs = ptsMs;                 // 实际帧时间
            frame.requestedMs = targets.at(targetIndex); // 请求时间
            output.append(frame);
            ++targetIndex;
        }
    };
    while (av_read_frame(...) >= 0) { /* send_packet → receive_frame → consumeFrame */ }

    // 5) flush 解码器残留帧（B 帧缓存）
    avcodec_send_packet(codecContext.get(), nullptr);
    while (avcodec_receive_frame(...) == 0) consumeFrame();
}
```

**五个工程细节（每一条都值得在面试中讲）**：

| 细节 | 作用 |
|---|---|
| 目标时间戳排序去重 | 保证"单次顺序解码"可行：指针 `targetIndex` 单调前进 |
| `interrupt_callback` | 用户取消时能打断 FFmpeg 阻塞在网络/慢盘 I/O 上 |
| RAII deleter（Format/Codec/Frame/Packet/Sws 五个） | 所有 FFmpeg 资源异常安全释放，零泄漏 |
| `best_effort_timestamp` + `av_rescale_q` | 处理 B 帧导致的 packet 顺序 ≠ 显示顺序；时间基换算到毫秒 |
| `requestedMs` 与 `ptsMs` 分离 | 检索/证据引用的是请求时间，实际帧时间用于精确对齐，避免时间漂移 |

**性能本质**：从 O(N × 打开+seek+落盘) 降为 O(1 次打开 + 1 次顺序解码)。seek 是随机 I/O，顺序解码是顺序 I/O，两者差距是数量级的。

### 4.5 线程模型与任务竞态处理

- 索引跑在 `QThreadPool`（`setMaxThreadCount(2)`）；
- **任务代际号机制**：每次 `startIndex` 时 `m_taskGeneration.fetch_add(1)`，任务在各阶段校验 `isTaskCurrent(taskId, videoId)`（generation + videoId 双条件），不匹配即静默退出；
- 取消 = `m_cancelRequested.store(true)` + generation 自增，配合 FrameExtractor 的 `interrupt_callback`，双层保险；
- 不用 terminate：暴力杀线程会留下半写的索引数据和锁状态。

## 五、真实工程问题（war stories，重点讲）

### 问题 1：取帧性能是索引的根因瓶颈

**现象**：索引一个 10 分钟视频，光抽帧就要几十秒，ONNX 推理反而快。
**定位**：profiler 显示时间耗在播放器 SDK 的 `extractThumbnail()`——每帧一次完整的 open→seek→decode→JPEG 落盘→读回→删除。
**解决**：独立 FrameExtractor（上文 4.4）。
**方法论（面试金句）**：**先重构取帧，再谈换模型**——索引链路的性能上限由最底层的数据获取决定；取帧是镜头切分、代表帧、OCR、embedding、最终引用的公共依赖，动一处收益全局。

### 问题 2：B 帧导致时间戳乱序

**现象**：有 B 帧的视频场景边界错位、时间戳偶尔回跳。
**原因**：packet 到达顺序 ≠ 显示顺序（解码顺序）。
**解决**：用 `best_effort_timestamp`（解码器输出的显示时间）而非 packet 时间；解码结束后 flush 解码器（`send_packet(nullptr)`）取出缓存的 B 帧。

### 问题 3：用户快速切换视频的索引竞态

**现象**：快速连续打开两个视频，第一个视频的索引数据混进了第二个视频的 RAG Store。
**解决**：
1. 任务代际号（旧任务自行退出）；
2. 新任务开始时 `invalidateVideo(videoId)` 清旧数据；
3. `m_repr`（表示缓存）用互斥锁保护，元信息在任务启动时按目标路径快照，播放器后续切换不覆盖。

### 问题 4：直方图对"渐变场景"漏检

**现象**：缓慢的灯光变化、推镜头，直方图差异始终低于阈值，整段不切。
**缓解**：TransNetV2 深度模型对渐变切换敏感得多；同时直方图阈值是可配置项。可以坦承这是兜底算法的已知局限，双算法分级就是为此设计的。

## 六、面试官可能问的问题

| 问题 | 回答要点 |
|---|---|
| **为什么四层而不是固定时长切分？** | 语义完整性：固定切分腰斩事件/浪费 chunk；分层让边界来自内容（镜头检测、ASR 语义段）。 |
| **Shot 和 Event 的区别？** | Shot 是物理边界（镜头切换检测），Event 是语义单元（按动作/ASR 语义合并，5~30s）。一个长镜头可含多个事件。 |
| **索引一个 10 分钟视频多久？** | L0 秒级（直方图 120 帧比较 <50ms + 取帧）；L1 主要耗在 CLIP 批量编码和 Whisper，后台线程不阻塞交互；L2 按需。二次打开秒级（索引缓存命中）。 |
| **关键帧为什么选首/中/尾？** | 最低成本的时序覆盖（开始/过程/结束三状态）。更精细的策略（运动剧烈处、OCR 变化处加密采样）是明确演进方向，当前版本选了最稳的实现。 |
| **videoId 为什么不全量 hash？** | 全量 hash 对大视频慢；SHA1(大小 + 前 1MB) 实践中足够区分编辑过的文件。 |
| **为什么索引不依赖播放器？** | 解耦：索引是离线批处理（顺序解码最优），播放器是实时随机访问（seek 最优），两者 I/O 模式根本不同；且索引跑后台不能干扰播放状态。 |
| **取帧支持局部密采样吗？** | 支持——`requestedMs` 是任意时间戳列表，排序去重后顺序消费；Agent 的 `analyze_time_range` 工具就是传一个区间的密集时间点列表。 |
| **怎么评估索引质量？** | 关键事件是否被抽到（标注集人工核）、镜头切分准确率、代表帧是否覆盖前后状态、ASR/OCR 时间戳误差。 |
| **如果视频 10 小时怎么办？** | 分片并行解码；增量索引 + 分段任务队列；L2 从"按需单场景"变"优先级队列 + 预算控制"；分层索引的意义就在此——Video/Event 粗粒度先召回再下探。 |

## 七、白板演练：一条完整链路

```
用户打开 meeting.mp4（10 分钟）
  │
  ├─ computeVideoId = SHA1(size + 前1MB) → "a3f8c2..."
  ├─ 首次打开：无缓存
  │
  ├─ [L0] 采样 60 帧（10s/帧，直方图模式）
  │   ├─ detectScenes: Bhattacharyya 距离 → 23 个场景
  │   ├─ assignRepresentativeFrames: 每场景 首/中/尾 ≤3 帧
  │   └─ persistKeyframes → AppData/keyframes/a3f8c2/
  │   → progress(30, "识别到 23 个场景")   ← 用户已可提问
  │
  ├─ [L1] 后台线程
  │   ├─ CLIP encodeImages(69 张代表帧) → 批量推理一次
  │   ├─ Whisper 转写 → SpeechSegmenter 语义分段（带时间戳）
  │   ├─ BGE 编码文本 → textEmbedding
  │   └─ insertChunks(visual_frames / text_segments)
  │   → progress(100, "索引完成 (视觉 69 / 文本 87)")
  │
  └─ 用户问"第 3 分钟白板上写了什么"
      └─ [L2 按需] compileQueryPlan 解析"第3分钟" → 该场景 VLM 深化
```
