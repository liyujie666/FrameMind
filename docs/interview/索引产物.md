# 一、整体索引产物

完整流程可以画成这样：

```text
视频文件
  │
  ├─ 视频元信息
  ├─ 均匀采样帧
  ├─ 场景切分
  ├─ 场景代表帧
  ├─ 视觉 Embedding
  ├─ Whisper 转写
  ├─ 语音语义窗口
  ├─ VLM 场景描述
  ├─ 可见文字与动作
  ├─ 音视频融合描述
  └─ 全视频摘要
        │
        ├─ VideoRepresentation：内存中的视频表示
        ├─ keyframes：本地关键帧图片
        ├─ rag_chunks：SQLite 中的 RAG Chunk
        ├─ rag_entities：实体档案
        └─ video_metadata / scene_descriptions：视频摘要和场景描述
```

---

# 二、第一类输出：视频元信息

## 1. 输出内容

每个视频会生成一份基础元信息：

```cpp
struct VideoInfo {
    QString filePath;
    QString fileName;
    QString format;
    int64_t durationMs;
    int64_t bitRate;
    double frameRate;
    int width;
    int height;
    bool hasAudio;
};
```

主要包括：

- 视频路径
- 文件名
- 视频时长
- 帧率
- 分辨率
- 比特率
- 是否包含音频

此外，`VideoIndexer::computeVideoId()` 会生成一个视频标识：

```text
videoId = SHA1(文件大小 + 文件头前 1 MB).left(16)
```

## 2. 如何构建

索引开始时，`VideoIndexer::startIndex()` 会：

1. 校验视频文件是否存在。
2. 计算 `videoId`。
3. 保存视频路径和文件名。
4. 从播放器或媒体探测结果中获得视频信息。

## 3. 保存在哪里

视频元信息主要进入内存中的：

```cpp
VideoRepresentation::metadata
```

部分持久化信息保存在 SQLite 的：

```sql
video_metadata
```

该表包含：

```text
video_id
video_path
video_summary
index_level
updated_at
```

当前数据库初始化路径由 `DIContainer` 设置：

```cpp
QStandardPaths::writableLocation(QStandardPaths::AppDataLocation)
    + "/agent.db"
```

在 Windows 上通常类似：

```text
C:\Users\<用户名>\AppData\Local\<组织名>\<应用名>\agent.db
```

实际目录由 Qt 应用组织名和应用名决定，因此不要在面试中死说某个固定绝对路径，可以说：

> 数据库位于 Qt 的 AppDataLocation 下，文件名为 `agent.db`。

## 4. 用途

元信息主要用于：

- 构建视频上下文。
- 解析时间范围。
- 计算采样点。
- 判断问题中的“开头、结尾、后半段”。
- 限制时间戳不能超过视频时长。
- 生成视频级摘要。
- 判断当前索引对应的是哪个视频。

# 三、第二类输出：场景和时序结构

## 1. 输出内容

场景是当前视频 RAG 的核心结构单元：

```cpp
struct Scene {
    int id;
    int64_t startMs;
    int64_t endMs;

    int64_t keyframeMs;
    QString keyframePath;
    QVector<SceneFrame> representativeFrames;

    QString description;
    QString visualDescription;
    QStringList visibleTexts;
    QStringList visibleActions;
    QString audioSummary;
    QString fusedDescription;
};
```

每个场景至少包含：

```text
scene_id
start_ms
end_ms
representative_frames
keyframe_path
```

如果完成了 Level 2 分析，还会包含：

```text
visual_description
visible_texts
visible_actions
audio_summary
fused_description
audio_relation
audio_relation_confidence
```

## 2. 如何构建

### 第一步：生成采样时间点

`VideoIndexer::computeSampleCount()` 根据视频时长计算采样数量。

当前策略是：

```text
有 TransNetV2：
    大约每秒 1 帧，最多 600 帧

无 TransNetV2：
    大约每 10 秒 1 帧，最多 200 帧
```

然后使用均匀采样：

```cpp
timestamp = (i + 0.5) / count * durationMs;
```

### 第二步：抽帧

正常路径通过：

```cpp
FrameExtractor::extract(videoPath, targets, ...)
```

批量提取视频帧。

如果 `FrameExtractor` 失败，才使用播放器的兼容回退方案。

### 第三步：场景检测

采样帧会传入：

```cpp
SceneDetector::detectScenes(frames, timestamps)
```

场景检测器负责根据视觉变化生成场景区间。

当前场景主要表示：

> 一段视觉上相对稳定的视频时间区间。

它不完全等价于“一个完整事件”。例如一个长镜头里可能仍然包含多个动作或事件。

### 第四步：为每个场景选择代表帧

`assignRepresentativeFrames()` 会在场景内部选择：

- 场景开始附近的一帧
- 场景中间的一帧
- 场景结束附近的一帧

每个场景最多三张代表帧。

这样设计的原因是：

> 单张首帧只能表示一个静态状态，首、中、尾三张帧可以初步表现人物、物体和状态变化。

## 3. 保存在哪里

场景对象首先保存在内存中的：

```cpp
VideoRepresentation::scenes
```

场景本身不是单独保存成一张 `scenes` 表，而是通过以下方式间接持久化：

- 场景摘要写入 `rag_chunks`
- 场景描述写入 `scene_descriptions`
- 关键帧路径写入对应的 Chunk
- 视频摘要写入 `video_metadata`

## 4. 用途

场景结构用于：

- 场景级检索。
- 时间定位。
- 组织代表帧。
- 选择 VLM 分析范围。
- 生成 `sceneOverview`。
- 响应“第几个场景发生了什么”。
- 支持 `get_scene_info` 和 `analyze_time_range` 工具。
- 将检索结果映射回播放器时间轴。

---

# 四、第三类输出：关键帧和代表帧图片

## 1. 输出内容

每个场景可能保存两类图片：

### 主关键帧

兼容旧的场景 UI：

```text
scene_<sceneId>_<keyframeMs>.jpg
```

例如：

```text
scene_5_32000.jpg
```

### 场景代表帧

用于视觉 Embedding 和 VLM 多帧分析：

```text
scene_<sceneId>_rep_<frameIndex>_<ptsMs>.jpg
```

例如：

```text
scene_5_rep_0_32000.jpg
scene_5_rep_1_35000.jpg
scene_5_rep_2_38000.jpg
```

## 2. 如何构建

由：

```cpp
VideoIndexer::persistKeyframes()
```

负责落盘。

图片保存为 JPEG：

```cpp
scene.keyframe.save(path, "JPG", 85);
frame.image.save(path, "JPG", 85);
```

Level 1 完成后，内存中的 `QImage` 会释放：

```cpp
scene.keyframe = QImage();

for (SceneFrame& frame : scene.representativeFrames) {
    frame.image = QImage();
}
```

但是图片路径仍然保留，因此后续可以按需从磁盘加载。

## 3. 保存在哪里

路径结构是：

```text
<AppDataLocation>/keyframes/<videoId>/
```

例如：

```text
C:\Users\<用户名>\AppData\Local\<组织名>\<应用名>\
keyframes\ab12cd34ef56abcd\
```

## 4. 用途

关键帧图片有四个用途：

### 用途一：视觉 Embedding

将代表帧送入 CLIP：

```cpp
m_clip->encodeImages(representativeImages);
```

生成视觉向量，用于视觉检索。

### 用途二：VLM 场景描述

VLM 按时间顺序读取场景内的代表帧，分析：

- 人物
- 物体
- 动作
- 状态变化
- 画面可见文字

### 用途三：证据回注

检索命中后，`EvidenceComposer::mergeFrames()` 会根据 `keyframePath` 加载图片，并将最多三张检索帧加入 VLM 输入。

### 用途四：时间定位和 UI 展示

图片路径可以作为检索结果的证据来源，结合 `startMs` 和 `endMs`，实现：

- 证据缩略图展示
- 时间戳点击跳转
- 回答追溯

# 五、第四类输出：视觉 Embedding

## 1. 输出内容

对场景代表帧编码后，会生成：

```cpp
std::vector<float> frameEmbedding;
```

每一张代表帧对应一个 `FrameDesc` Chunk。

该 Chunk 的主要内容是：

```text
chunk_id
video_id
start_ms
end_ms
chunk_type = FrameDesc
frame_embedding
keyframe_path
scene_id
keyframe_ms
frame_role
embedding_model_id = clip_visual
embedding_version = 1
embedding_dimension
file_path
```

## 2. 如何构建

Level 1 阶段会收集全部代表帧：

```cpp
std::vector<QImage> representativeImages;
```

然后批量调用：

```cpp
m_clip->encodeImages(representativeImages);
```

随后为每张图片创建一个 Chunk：

```cpp
chunk.chunkType = VideoChunk::FrameDesc;
chunk.frameEmbedding = embeddings[embeddingIndex];
chunk.keyframePath = frame.imagePath;
```

## 3. 保存在哪里

视觉 Chunk 写入：

```cpp
VideoRAGStore::VisualFrames
```

SQLite 中对应：

```text
rag_chunks.collection = "visual_frames"
rag_chunks.frame_embedding
```

表结构大致是：

```sql
rag_chunks (
    chunk_id,
    collection,
    video_id,
    start_ms,
    end_ms,
    chunk_type,
    text_content,
    text_embedding,
    frame_embedding,
    keyframe_path,
    metadata_json
)
```

向量会以 BLOB 的形式保存。

同时，`VideoRAGStore` 会把 Chunk 放进内存：

```cpp
inMemory[VisualFrames][chunkId] = chunk;
```

## 4. 用途

视觉 Embedding 用于：

- 以文本找画面。
- 查询人物、颜色、物体和场景。
- 找语义上相似的视觉片段。
- 支持“穿红衣服的人在哪”“画面中有没有汽车”等问题。

需要注意：

> CLIP 向量本身不保存可读描述，它只负责相似度检索。真正用于回答的画面细节还需要通过代表帧回注 VLM。

# 六、第五类输出：Whisper 原始转写段

## 1. 输出内容

Whisper 会输出带时间范围的语音段：

```cpp
struct SpeechSegment {
    int64_t startMs;
    int64_t endMs;
    QString text;
};
```

例如：

```text
[32000, 36000]  “我们接下来分析线程池的工作机制”
```

## 2. 如何构建

Level 1 阶段：

1. 使用 `AudioDecoder` 解码视频音频。
2. 转成 Float32 PCM。
3. 调用：

```cpp
m_whisper->transcribe(pcmData);
```

4. 得到带时间戳的 `SpeechSegment`。

## 3. 保存在哪里

原始语音段会进入：

```cpp
VideoRepresentation::speechSegments
```

同时写入 `VideoRAGStore::TextSegments`。

对应 Chunk：

```text
chunk_type = SpeechSegment
text_content = Whisper 原文
start_ms
end_ms
embedding_model_id = bge_text
embedding_version = passage_v2
source = whisper
evidence_type = speech_segment
```

SQLite 中仍然是：

```text
rag_chunks.collection = "text_segments"
```

文本 Embedding 保存到：

```text
rag_chunks.text_embedding
```

## 4. 用途

原始转写段主要用于：

- 字幕展示。
- “他说了什么”。
- 精确引用原话。
- 获取指定时间区间的字幕。
- 音视频时间对齐。
- 旁白和同期对话分析。
- 文本语义检索。
- 词面检索。

原始段通常较短，因此适合精确定位，不一定适合作为完整主题检索单元。

---

# 七、第六类语音语义窗口

## 1. 输出内容

`SpeechSegmenter::buildSemanticSegments()` 会将多个较短的 Whisper 段合并成较长的语义窗口。

当前目标窗口大约是：

```text
12 到 30 秒
```

例如原始转写：

```text
[00:10, 00:13] 线程池可以复用线程
[00:14, 00:17] 避免频繁创建和销毁
[00:18, 00:22] 从而降低调度开销
```

可能合并成：

```text
[00:10, 00:22]
线程池可以复用线程，避免频繁创建和销毁，从而降低调度开销。
```

## 2. 如何构建

构建逻辑是：

```cpp
SpeechSegmenter::buildSemanticSegments(
    repr->speechSegments
);
```

然后每个语义窗口创建一个 `Event` 类型的 Chunk。

## 3. 保存在哪里

同样保存到：

```text
VideoRAGStore::TextSegments
```

Chunk 的主要标记是：

```text
chunk_type = Event
evidence_type = speech_semantic
source = whisper_semantic
embedding_model_id = bge_text
embedding_version = passage_v2
```

## 4. 用途

它和原始语音段用途不同：

| 类型 | 主要用途 |
|---|---|
| `SpeechSegment` | 原话、字幕、精确时间定位 |
| `Event` / `speech_semantic` | 主题检索、连续语义理解 |

这是一个比较重要的设计点，面试可以这样说：

> 原始 ASR 段服务于精确引用和时间对齐，语义窗口服务于主题级召回，两种粒度分别解决精准定位和语义完整性问题。

# 八、第七类 VLM 场景视觉描述

## 1. 输出内容

VLM 对每个场景的多张代表帧进行分析，生成结构化结果：

```json
{
  "visual_description": "讲师介绍线程池的基本工作机制",
  "visible_text": ["Thread Pool"],
  "actions": ["讲解线程复用过程"],
  "uncertain": [],
  "confidence": 0.86
}
```

代码会提取：

```text
visual_description
visible_text
actions
```

## 2. 如何构建

多帧网格方案将同一场景内按时间排序的代表帧绘制到一张大图中，再交给 VLM 联合分析。以下是接入 `VideoAnalysisService::doDescribeSceneWithCallback()` 的网格化构建方案；当前代码仍采用多张图片联合输入。

1. **选择并加载代表帧**：覆盖场景开始、中间和结束等不同状态。三张帧可以组成 1×3 网格；需要 3×3 网格时，应在场景内补充抽取至多九张有效帧，而不是重复现有图片凑数。
2. **按实际时间排序**：依据每张帧的 `ptsMs` 排序，并建立“帧编号 → 实际时间戳 → 原图路径”的映射，供后续引用和复核。
3. **统一格子尺寸**：例如每格使用 `384×216` 的图像区域，等比例缩放，宽高比不一致时留边，避免拉伸或裁掉画面内容；另预留 `24` 像素高的标签条。
4. **绘制网格图片**：创建一张 `QImage` 画布，使用 `QPainter` 按“从左到右、从上到下”的时间顺序绘制各帧、边框和标签。标签包含 `F1`、`F2` 等帧编号及实际视频时间戳。按上述尺寸，九张帧组成的 3×3 网格在不计边距时为 `1152×720`。
5. **构造时序分析提示词**：结合视频类型，明确说明各格来自同一场景、网格阅读顺序和时间标签含义，要求分析人物、物体、动作及状态变化，区分可见事实与推断；采样间隔内未展示的动作或看不清的文字应标记为不确定。
6. **将网格作为单张图片输入 VLM**：一次请求分析整个场景的多个时间状态。模型获得的是带时间标记的离散采样画面，不能据此保证连续动作理解或精确到帧的事件定位。
7. **解析并保存结构化结果**：提取 `visual_description`、`visible_text` 和 `actions`，沿用场景描述与检索证据的存储流程。若扩展支持帧编号字段，还需同步增加解析与持久化逻辑，将观察结果关联回原图和时间戳。

> 多帧网格的核心是把时间序列组织成带编号和时间标签的空间布局，让 VLM 同时观察前后状态。原始代表帧仍应单独保存并分别生成视觉向量，网格用于场景概览，原图用于细节检索与复核。

网格化会降低单帧的有效分辨率，因此读取 PPT 小字、代码或招牌时，应补充高分辨率原图或局部裁剪。当前多图联合输入本身也只需一次请求，不能把改用网格直接表述为“模型调用次数降低九倍”；实际图像 Token 和费用取决于模型的缩放、切块与计费规则。

## 3. 保存在哪里

视觉描述保存在：

```cpp
VideoRepresentation::sceneVisualDescriptions
```

键为：

```text
sceneId → visualDescription
```

同时保存到数据库：

```sql
scene_descriptions (
    video_id,
    scene_id,
    description,
    visual_description
)
```

此外，视觉描述也会写成 RAG Chunk：

```text
collection = text_segments
chunk_type = SceneSummary
evidence_type = visual
text_content = 视觉描述
start_ms = 场景开始时间
end_ms = 场景结束时间
scene_id = 场景 ID
```

## 4. 用途

视觉描述用于：

- 场景级文本语义检索。
- 生成视频摘要。
- 给 LLM 提供可读的画面上下文。
- 支持“这一段发生了什么”。
- 作为代表帧的文本语义投影。
- 为音视频融合提供视觉基线。

要注意：

> 场景描述是对原始帧的语义压缩，不能完全替代原始帧。因此生成回答时还要将代表帧回注给 VLM。

# 九、第八类画面可见文字和动作

## 1. 输出内容

VLM 会提取：

```cpp
QStringList visibleTexts;
QStringList visibleActions;
```

例如：

```text
visibleTexts:
    - "Thread Pool"
    - "Worker Thread"
    - "Task Queue"

visibleActions:
    - "讲师指向右侧流程图"
    - "展示线程复用过程"
```

## 2. 如何构建

这些字段来自场景描述 VLM 的结构化 JSON：

```cpp
scene.visibleTexts = jsonStringList(object, "visible_text");
scene.visibleActions = jsonStringList(object, "actions");
```

当前画面文字来源主要是：

```text
VLM 可见文字转录
```

不是独立的 PaddleOCR 或 Tesseract OCR 引擎。

## 3. 保存在哪里

画面文字会作为单独的证据 Chunk 写入：

```text
collection = text_segments
chunk_type = Event
evidence_type = visible_text
source = vlm_visible_text
text_content = visibleTexts.join("\n")
```

动作信息主要保留在内存中的 `Scene` 对象中，是否写入独立 Chunk 取决于后续场景证据写入逻辑。

## 4. 用途

画面文字用于：

- 检索 PPT 标题。
- 检索屏幕字幕。
- 查找界面按钮。
- 查找白板、图表和标语。
- 回答“屏幕上写了什么”。
- 配合视觉帧做证据核实。

# 十、第九类音视频融合证据

## 1. 输出内容

音视频融合会产生：

```cpp
struct SceneFusion {
    int sceneId;
    QString visualDescription;
    QString audioSummary;
    QString fusedDescription;
    AudioVisualGate gate;
    AudioVisualRelation relation;
    float confidence;
};
```

重点字段是：

```text
visualDescription
audioSummary
fusedDescription
relation
confidence
```

## 2. 如何构建

音视频融合分两步。

### 第一步：时间对齐

`AudioVisualAligner` 根据时间区间找到场景对应的语音段：

```text
scene.startMs < speech.endMs
&& speech.startMs < scene.endMs
```

### 第二步：语义门控

程序计算：

- 语音时间覆盖率。
- 视觉与语音的语义相似度。
- 关键词交集。
- 语音是否跨越多个场景。
- 语音与场景的关系。

然后把这些量化信号和视觉描述、同期转写一起交给 VLM 判断：

```text
同期对话
画外音
背景媒体
无关音频
未知
```

## 3. 保存在哪里

内存中：

```cpp
VideoRepresentation::sceneFusions
```

场景对象中：

```cpp
scene.audioSummary
scene.fusedDescription
scene.audioRelation
scene.audioRelationConfidence
```

RAG 层分别写入：

```text
SceneSummary → 纯视觉描述
SceneAudio   → 音频摘要
SceneFused   → 融合描述
```

它们都进入：

```text
VideoRAGStore::TextSegments
```

而不是把三种信息覆盖成一条文本。

## 4. 用途

不同问题使用不同证据：

| 问题 | 优先证据 |
|---|---|
| “画面里有什么？” | `SceneSummary` |
| “他说了什么？” | `SpeechSegment` 或 `SceneAudio` |
| “这段发生了什么？” | `SceneFused` |
| “画面中的 PPT 写了什么？” | `visible_text` + 代表帧 |
| “旁白和画面有什么关系？” | 音视频对齐和融合证据 |

这是项目中一个比较有价值的设计：

> 视觉事实、音频事实和融合推断分别保存，避免融合错误污染原始证据。

# 十一、第十类视频级摘要

## 1. 输出内容

全视频摘要是一个字符串：

```cpp
VideoRepresentation::videoSummary
```

内容通常是对所有场景描述的总结，例如：

```text
视频主要介绍线程池的基本概念、工作流程和使用场景，
中间通过代码示例说明线程复用和任务队列的关系。
```

## 2. 如何构建

流程通常是：

```text
场景视觉描述
    +
音视频融合描述
    ↓
按时间顺序拼接
    ↓
调用 LLM/VLM 汇总
    ↓
生成 videoSummary
```

## 3. 保存在哪里

内存中：

```cpp
VideoRepresentation::videoSummary
```

数据库中：

```sql
video_metadata.video_summary
```

## 4. 用途

视频摘要用于：

- 回答“视频讲了什么”。
- 作为系统提示词中的视频背景。
- 在没有精确检索命中时提供全局上下文。
- 生成视频目录和知识页。
- 支持全局摘要类问题。

它不是精确检索索引，不能承担所有细节问答。

# 十二、第十一类实体档案

## 1. 输出内容

项目还定义了实体结构：

```cpp
struct EntityProfile {

    EntityType type;
    QString primaryDescription;
    QStringList aliases;
    QVector<EntityAppearance> appearances;
    std::vector<float> descriptionEmbedding;
};
```

实体可以是：

- 人物
- 物体
- 地点
- 画面文字

实体档案包含：

```text
实体描述
别名
出现的场景
出现时间
可选的边界框
实体 Embedding
```

## 2. 如何构建

实体由：

```cpp
EntityTracker
```

负责维护和写入。

它不是 `VideoIndexer::buildLevel1()` 中自动生成的主要产物，而是 Agent 后续分析或实体追踪流程产生的结果。

因此你要区分：

> 实体索引在系统架构中存在，但不一定由每次视频基础索引自动完整生成。

## 3. 保存在哪里

实体档案保存到：

```sql
rag_entities
```

同时会生成一个用于检索的实体 Chunk：

```text
collection = entity_profiles
chunk_type = Event
text_content = entity.primaryDescription
text_embedding = entity.descriptionEmbedding
metadata.entity_id
metadata.entity_type
```

## 4. 用途

实体索引用于：

- “那个穿红衣服的人”。
- “刚才出现的车辆”。
- “这个人后来去了哪里”。
- 跨场景聚合人物或物体。
- 解决实体指代问题。

## **补充：持久化位置与索引级别对应关系**

```text
Level 0 (即时, <1秒):
    ├─ VideoRepresentation (内存: metadata, scenes边界)
    └─ 本地关键帧目录 (代表帧图片)

Level 1 (后台, 秒~分钟):
    ├─ rag_chunks (视觉帧 Chunk, 语音 Chunk, 语义窗口 Chunk)
    └─ 本地关键帧目录 (用于编码后即可复用)

    ├─ rag_chunks (场景视觉/音频/融合描述 Chunk, 可见文字 Chunk)

    ├─ rag_entities (Agent 分析过程中积累)
    └─ rag_chunks (QA Cache, 用户问答后写入)
```




# 十五、你可以用一句话记忆整个索引

> 我的视频 RAG 索引不是只生成一个向量，而是围绕统一时间轴构建了多类可追溯证据：先通过抽帧和场景检测生成视频时序骨架，再分别提取代表帧、视觉向量、ASR 原始转写和语义窗口，之后由 VLM 生成场景视觉描述、画面文字和动作信息，并通过音视频对齐生成独立的音频和融合证据。最终，原始帧保存到本地关键帧目录，文本、向量、时间戳和元数据保存到 SQLite 的 `rag_chunks`，场景描述保存到 `scene_descriptions`，视频摘要保存到 `video_metadata`，实体信息保存到 `rag_entities`，共同支持后续的多路检索、证据回注和视频问答。

# 十六、面试时最推荐的回答方式

面试官问：

> “你的视频 RAG 索引具体构建了哪些东西？”

你可以这样回答：

> 我们不是只对视频做一次整体 Embedding，而是围绕时间轴构建多粒度、多模态索引。
>
> 首先是结构索引。通过 FFmpeg 抽取均匀采样帧，再结合场景检测得到场景的开始时间、结束时间和场景 ID，每个场景保留开始、中间、结束三张代表帧，关键帧以 JPEG 形式持久化。
>
> 第二是视觉索引。对这些代表帧使用 CLIP 编码，每张代表帧形成一个带时间戳、场景 ID 和图片路径的视觉 Chunk，向量和元数据保存到 `rag_chunks` 的视觉集合中。
>
> 第三是音频索引。通过 Whisper 对音轨进行转写，保留带时间戳的原始语音段，同时把多个短段合并成语义窗口。原始段用于字幕、精确引用和音视频对齐，语义窗口用于主题级检索。
>
> 第四是语义证据。对场景内的多张代表帧调用 VLM，提取纯视觉描述、画面文字和动作；再通过时间重叠、语义相似度和跨场景信息与同期语音进行对齐，分别保存视觉、音频和融合证据。
>
> 这些结果分别保存到本地关键帧目录、SQLite 的 `rag_chunks`、`rag_entities`、`video_metadata` 和 `scene_descriptions` 中。在线检索时，文本、视觉、实体和词面检索都返回带时间区间的 Chunk，最后把文本证据和代表帧组成证据包交给 VLM 生成可追溯回答。

你只需要牢记三层关系：

```text
原始证据：
帧、音频、ASR、VLM 识别的文字

检索表示：
```
