## 1. 交付目标与边界

最终交付必须同时具备：单元之间有限并发、单元内部逐页串行、滚动关键上下文、每页零或一张网格图，以及可复现的性能和质量对照数据。

实施起点是 `prepareUnitEvidence()` 完成补帧和快照保存，终点是所有单元理解结束后的完成屏障。继续使用现有分类、分段校正、ASR、原始帧提取、CLIP/BGE、总结及事务发布流程。允许为单元理解扩展网络诊断、图片编码和请求接口。

[内容质量设计](video-analysis-content-quality-design.md)涉及单元综合、内容章节、类型化笔记和 UI，作为接口协同事项，不计入本计划交付。这里提供独立页结果与统一的单元完成入口，供其后续接入；不能把章节整理追加为每页额外串行请求。完成本计划不能宣称章节、笔记或 UI 改造也已完成。

以下现状来自源码静态核对；未在本次规划中重新构建、运行测试或调用在线模型。

## 2. 当前代码与实施缺口

| 代码位置 | 核对结果 | 实施要求 |
|---|---|---|
| `video_rag_build_coordinator.cpp` 的 `Job`、`analyzeNext()` | 共用 `unitIndex/pageIndex/pages/retryReason`，回调以当前全局游标定位单元 | 拆成独立任务；按固定序号写入；回调携带完整请求身份 |
| `analyzeNext()` 尾部 | 当前负责父单元归并、摘要输入及零成功页分支 | 拆为单次屏障后的归并函数；活跃请求期间不向单元容器追加父单元 |
| `request()` | 有模型签名、generation、回调去重和 watchdog；超时使用构建取消 key | 保留保护机制，单元请求改为指定 requestId 取消 |
| `OneShotVlmChannel` | 专属 Agent，内部严格串行；有 idle/total watchdog 和构建级取消 | 保持单通道串行，新增请求级身份与取消，并明确取消后的终态回调 |
| `DIContainer` | 聊天与后台视觉链路已经分离，但后台只有一组客户端 | 增加有界单元理解工作池，保留现有后台／局部分析通道 |
| `AgentService::sendOneShot()` | 单实例保存当前会话和累计流式状态；已有请求诊断计时 | 每个 worker 使用独立实例；共享配置只能在同一 QObject 线程读取 |
| `AgentService::makeUserMessage()` | 图片统一缩到 1024 内，JPEG 80 | 引入专用编码选项，网格不得再次缩回旧上限 |
| `UnitEvidencePage` | 有 `framePaths/framePtsMs`，`sourceIds` 同时包含文字和图片来源 | 增加明确的逐帧 sourceId/PTS/path 对应关系，不能按混合 sourceIds 下标配对 |
| `validatedFacts()` | 已限制事实类型及本页来源，并根据原始帧数量处理 operation | 继续以原始证据页校验，不能把一张网格误当作一个原始帧 |
| `ModelReply` | 只有 `content/error` | 增加可选结构化状态／诊断，支持可靠识别 429、临时错误和 Retry-After |
| `VideoRAGBuildPlan` | JSON codec 与整份计划 fingerprint 已存在 | 增加理解合同及网格参数版本；并发额度放运行配置，避免无谓改变证据兼容性 |
| 测试及 CMake | 已有 RAG、模型通道、tokenizer、媒体四类测试；RAG target 不链接完整网络链路 | 保留轻量协调器注入接口，另用模型通道测试验证生产工作池真实网络重叠 |

## 3. 实施阶段与依赖

依赖顺序：P0 → P1 → P2 → P3 → P4 → P5 → P6。P1 起加入公共观测字段，P2 起保存对照能力，避免等到性能验收时重新修改请求链路。

| 阶段 | 可验收交付 | 预计工作量 |
|---|---|---:|
| P0 基线与合同冻结 | 工作区差异清单、基线回归、请求／页结果合同 | 0.5～1 人日 |
| P1 请求隔离与工作池 | 独立客户端、指定请求取消、错误元数据、生命周期管理 | 2～3 人日 |
| P2 单元任务与调度 | 真并发、页内串行、按序归并、单次屏障、页进度 | 2～3 人日 |
| P3 滚动关键上下文 | 事实短编号、合同校验、预算及程序降级 | 1.5～2.5 人日 |
| P4 网格与编码 | 来源完整映射、网格布局、专用编码、必要拆页 | 2～3 人日 |
| P5 集成与兼容回归 | 指纹、诊断汇总、发布／恢复及构建矩阵 | 1～2 人日 |
| P6 真实模型对照验收 | A/B/C/D 数据、质量审查、默认参数及验收记录 | 2～4 人日 |

总计约 11～18.5 人日，是基于静态代码范围的估算，不是固定交付日期。按一名熟悉项目的开发者顺序执行约 2～4 周；真实素材准备、模型配额和等待时间另计。P0/P6 可依据实际风险调整估算。

### P1：请求隔离与有界工作池

涉及 `one_shot_vlm_channel.*`、新增 `unit_analysis_worker_pool.*`、`agentservice.*`、`networkclient.*`、`model_reply.h`、`dicontainer.*` 和 CMake。

- [ ] 为通道新增显式 requestId，提供 `cancelRequest(requestId)`；旧 enqueue／构建取消入口保持兼容。
- [ ] 实现最多 3 个独立 worker，每个持有自己的 NetworkClient、AgentService、OneShotVlmChannel；支持额度 1/2/3。
- [ ] 单元独占一个 worker 直至全部页结束；worker 内最多一个请求；分类／校正／总结继续走原通道。
- [ ] 明确池、客户端、协调器析构顺序；析构和整构建取消先停止调度再终止在途任务，不遗留定时器或占用槽位。
- [ ] 将 HTTP 状态、Retry-After、请求计时等作为可选结构化元数据贯穿回复；保留现有错误字符串兼容性，不用解析错误文案判断限流。
- [ ] 使用非阻塞定时器执行有界退避；429／临时错误消耗同一页唯一重试额度，明确最大等待预算，避免通道、Agent 和协调器各自叠加重试。
- [ ] 单请求 watchdog 只取消对应 requestId；取消完成后才能重试。整构建取消向池及原后台通道广播。

出口：本地 HTTP/SSE 测试服务观测到多个独立客户端请求重叠；取消一个请求不会取消另一 worker；聊天和局部分析原有行为通过回归。

### P2：从全局游标改为独立单元任务

涉及 `video_rag_build_coordinator.*`、`video_rag_build_coordinator_channel.cpp`、测试夹具及工作池接口。

- [ ] 在补帧完成后一次建立叶子单元任务及全部页描述，固定 unitOrdinal；只保留页路径和元数据，不预载全部图片。
- [ ] 将 `analyzeNext()` 拆为启动理解、填充空闲 worker、准备当前页、处理回复、完成单元、完成屏障等入口。
- [ ] 每个任务独立保存页游标、attempt、重试原因、结果及 coverage；不可捕获会变动的全局 unitIndex/pageIndex。
- [ ] 读图和后续合成使用有界后台准备任务，提交不可变输入，结果回协调器线程；后台完成同样检查构建和请求身份。
- [ ] 页最终成功或失败才推进游标；同页重试不增加完成数，下一页不提前请求。
- [ ] 单元结束立即填充空闲槽位；叶子任务全部终态后只执行一次父单元归并、摘要输入准备及现有发布分支。
- [ ] 空任务、无单元、全部页失败和部分失败均可收敛；失败原因独立保存，异步到达顺序不改变结果顺序。
- [ ] 理解区间沿用现有进度范围，按“已确定页面数／固定总页数”推进；文字展示活跃单元数和页数。
- [ ] 提供专用单元请求注入接口；生产接工作池，离线夹具可控制并发和终态，原有其他阶段 mock 不必依赖真实网络。

出口：在额度 3 下出现跨单元请求重叠，同一单元始终只有一个在途页；乱序、重复及迟到回调不能改变归并顺序或重复启动总结。额度 1 通过相同调度路径。

### P3：滚动关键上下文

新增建议模块 `src/service/rag/unit_carry_context.h/.cpp`，调整类型策略的页 Prompt 和单元请求 JSON。

- [ ] 使用单次页理解输出本页结果及 carry，不新增独立记忆压缩请求。
- [ ] 为已接受事实建立单元私有短编号池；当前页新 facts 仍只允许引用当前页原始来源。
- [ ] carry 校验 topic、current_state、key_fact_refs、pending_threads、uncertainties，以及引用所属单元与页序。
- [ ] next-page JSON 按 Compact 序列化后的 QString 字符数执行初始 1000 字符硬预算，计入展开事实；记录此口径，不能当 token 数。程序补入页进度与 gap_count。
- [ ] 按优先级保留完整条目和有效引用；替换过时状态，移除已解决事项，保留仍必要的早期事实。已确认状态必须有有效事实引用。
- [ ] carry 单独无效时保留主结果，以上一有效 carry 加当前少量已接受事实进行程序降级；超长时裁剪条目，不截断 JSON。
- [ ] 最终失败页不生成事实，增加缺口标记；下一成功页不能凭上下文补造缺失过程。重试使用完全相同的输入 carry。
- [ ] 保留类型关注点，summary 融合描述新增内容；证据和上下文内的指令作为分析内容处理。

出口：早期事实可跨多页保留，预算和引用有效；主结果成功但 carry 失败不增加模型调用；跨单元引用、未知编号和未来页编号均被拒绝。

- [ ] 按 PTS 和稳定来源顺序排序；实现 1 帧 1×1、2 帧 2×1、3～4 帧 2×2、5～6 帧 2 列×3 行。
- [ ] 使用 QImage/QPainter 等程序绘制，保持画面比例、标签独立置顶、空格明确标空，不覆盖或裁掉正文。
- [ ] 校验原始帧均可读且映射一一对应，读取失败按页失败记录具体来源；原始帧数、传输图片数、覆盖数分开统计。

- [ ] 有图页发送一张图，纯文本页发送零张；网格派生 ID 不进入事实来源，CLIP 仍编码原始帧。

出口：所有布局、横竖画面、同 PTS 多来源、纯文本和损坏图片用例通过；编码后的教程代码、字幕、课件和按钮名达到样本要求。

## 4. 必须覆盖的自动化用例

| 类别 | 关键用例 | 推荐归属 |
|---|---|---|
| 请求生命周期 | 指定请求取消、排队取消、超时与回复竞态、重复完成、worker 析构、HTTP 429/Retry-After | 模型通道／工作池测试 |
| 真并发 | 本地服务器同时接受多个 worker；额度 1/2/3；同 worker 串行；聊天隔离 | 模型通道／工作池测试 |
| 单元调度 | 乱序完成、同单元不重叠、队列补位、重试不推进、零页、全部失败、一次总结屏障 | `video_rag_tests` 及夹具 |
| 取消与身份 | 整构建取消、切视频、迟到回复、重复回调、模型签名改变、旧图片准备回调 | `video_rag_tests` 及模型通道测试 |

夹具应根据明确的阶段／输入字段返回响应。不能用默认 summary 回复掩盖新合同缺失；必须捕获实际提交的 carry、图片数量、requestId 和在途计数，不能只断言最终构建成功。

## 5. 建议实施批次

每批次包含对应测试，后批次依赖前批次；不要仅按新增文件拆提交。

1. 请求身份、取消合同、错误诊断与有界工作池（P1）。
2. 协调器独立单元任务、调度、屏障、进度及 B 对照入口（P2）。
3. carry 模型、引用校验、Prompt、降级及 C 对照入口（P3）。
4. 逐帧映射、网格、专用编码、必要拆页及 D 对照入口（P4）。
5. 计划指纹、诊断汇总、完整回归与兼容记录（P5）。
6. 真实模型对照、参数确认和验收报告（P6）。

这些批次可独立审查，但正式功能完成必须覆盖全部阶段。正式默认参数在 P6 决定，设计建议的 C=3、1000 字符、2048/JPEG85 是初始验证参数。
