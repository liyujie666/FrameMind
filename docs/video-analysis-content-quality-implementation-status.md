## 2. P0 请求合同与可控夹具

旧阶段为 classify、segment、understand、summarize。`FixtureStageContract` 按旧输入结构／明确 Prompt 识别；未知请求返回 `fixture_error`，不会默认截取输入生成成功摘要。

新阶段的请求信封版本为 `content_quality_request_v1`：

```json
{"stage":"unit_synthesis","contract_version":"content_quality_request_v1","payload":{}}
```

P0 固定阶段标识及必需的对象信封；下面是 P2～P6 的字段合同准备稿，P2 冻结字段、枚举、默认预算和正式校验后才能接入生产。当前生产请求未改用此信封。

| stage | 预定 payload 内容 | 输出约束／实施阶段 |
|---|---|---|
| unit_synthesis | unit_id、完整 pages、facts、coverage | title、summary、带来源 points；来源为本单元，P3 |
| synthesis_reduce | 完整页／事实组、来源映射、归约层 | 原子组与来源保留，单轮工作量下降，P3 |
| chapter_plan | 时间排序叶子单元、不可用区间 | 连续 unit_ids 分组和标题；程序计算时间／ID，P4 |
| chapter_merge | 相邻窗口分组、边界单元 | 去重与连续覆盖，无跨缺口虚构，P4 |
| chapter_refine | 全片提纲、当前证据、邻接概要 | 当前章节正文及有效来源，P4 |
| overview_reduce | 全片章节／事实组、归约层 | 内部归约，不创建虚假 ChapterSummary，P5 |
| overview | 完整提纲、事实、缺口 | 独立全片概览，错误与统计不入正文，P5 |
| typed_content | 类型 policy、证据、章节 | 受控 sections／entries／points，P6 |
| explore_questions | policy、已理解证据 | 有来源问题；程序生成锚点，P6 |

`FixtureModelScript` 保存待回复回调，测试可按任意顺序调用 deliver、重复投递、不投递以触发 watchdog、取消后再投递，以及提供非法来源／错误回复。新阶段默认没有生成器，必须显式编写回复。`stageFixtureRejectsUnknownContracts` 验证未知阶段／版本失败；页并发、超时、非法引用、取消迟到和重复回复继续由既有 RAG 测试验证。

## 5. P1 实现与验证

协调器新增 buildStarted、buildProgress、buildTerminated、representationReady、buildProfileReady。前三者携带 VideoBuildContext，终态另带实际 manifest；旧 progress／published／finished、Service 的旧信号保留兼容。终态统一去重；新 run 建立后才重放旧结果。取消、失败、缓存复用和新发布都结束对应 run；已提交活动版本不会被同步重入的取消改写。

Service 转发带身份事件，并保存当前运行上下文和同一 representation 快照。VM 只由匹配路径／buildId／taskGeneration 的事件改变运行状态，分别保存 runningBuildId 和 displayedBuildId；接受本次结果或本次明确重放的 expectedActiveBuildId。summaryReady、无身份 indexer 进度和旧 buildFinished 不再结束当前任务。首次打开可恢复 Service 已启动的 run。总结页初次绑定同时恢复摘要和进度，概览就绪只更新卡片；失败／取消不会伪造 100% 进度。

新增 Widgets 测试使用实际 Service、VM、SummaryTabWidget 和协调器；只注入离线执行后端／模型回复，未替换被测生命周期实现。

### 7.2 类型与 Builder 合同

`VideoPresentationPolicyRegistry` 覆盖 Unknown、Tutorial、Educational、Interview、Presentation、Meeting、Documentary、Drama、News、Vlog 以及 demo。区域标题与 kind、条目 kind、point role、question intent 和 attributes 均受策略白名单约束。仅 Meeting 的第二块允许 action_item，owner／deadline 可缺省、null 或空字符串，读取为无值；其他条目不允许任意属性。每种策略保存内容指导，demo 只整理可见功能与表现，保留主类型。实际 demo 选择依据在 P6 接入。

Builder 提供显式阶段请求 envelope（`content_quality_request_v1`）、Prompt、严格 JSON 解析、单元综合校验、展示／单元校验、按实际 parent 关系识别叶子及归约收敛检查。Builder 不执行网络请求、不创建 worker、不管理取消或推进阶段。页请求继续走原有通道，新增阶段将由 P3～P6 通过协调器 request() 调度。

### 7.3 冻结预算默认值与合法范围

| 参数 | 默认 | 合法范围／口径 |
|---|---:|---|
| page_input_chars | 12000 | 字符类配置均为 256～262144，按 QString UTF-16 code unit 计数 |
| synthesis_input_chars | 24000 | 同上；用于完整单元／综合归约请求 |
| chapter_window_chars | 32000 | 同上；章节／概览／区域请求的字符保护 |
| max_output_chars | 16000 | 超限回复拒绝解析，不截断正文充当成功 |
| fallback_input_chars | 8000 | 无生成模型精确计数时的保守输入上限 |
| max_page_bytes | 65536 | 1024～1048576，紧凑 JSON UTF-8 字节 |
| max_unit_bytes | 1048576 | max_page_bytes～8388608 |
| max_presentation_bytes | 2097152 | 1024～16777216 |
| max_manifest_bytes | 3145728 | max_presentation_bytes～33554432 |
| max_reduction_depth | 4 | 1～8；每轮结果条目数须严格减少且非零 |
| max_requests | 4096 | 1～10000；整个构建模型请求的实际尝试，包括旧阶段与重试 |
| max_retries | 1 | 0～2；同 operationId 的 attempt 从 0 连续递增 |
| model_context_tokens | 0（未知） | 0～2097152；调用方提供当前生成模型上下文能力，不能借用 embedding tokenizer |
| reserved_output_tokens | 4096 | 1～131072 |
| protocol_overhead_tokens | 1024 | 0～65536；已知上下文须大于输出预留＋协议预留 |

精确 TokenCounter 可用且上下文已知时，计数包含 Prompt 和完整请求 envelope（policy／versions／payload），检查可用 token 额度，并同时保留字符保护。无精确计数时，采用 fallback 上限；若上下文已知，再按剩余额度／4 的保守字符保护收紧上限。四 token／UTF-16 单元仅是防护策略，不是精确计数或所有未知模型均支持输入的证明。当前业务尚未提供生成模型的精确 tokenizer，默认上下文保持未知。

`VideoPresentationRequestLedger` 在提交前 reserve，拒绝重复尝试、跨阶段复用 operationId、超次重试与总请求耗尽；finish 按操作与尝试去重。calls 计已预留提交的尝试，retries 计 attempt>0，failures 计调用方报告的请求／解析／来源校验失败，elapsed_ms 为各次请求耗时之和（并发时可以大于阶段墙钟耗时）。调用方须在模型与内容校验完成后 finish，并在取消时收尾。拒绝预留的请求不增加 calls。

阶段统计保存于 artifacts.presentation_stages，保留既有 artifacts.unit_analysis 和其他字段。归约／接缝调用合并到所属阶段统计：unit_synthesis、chapter_planning、chapter_refinement、overview、primary_section、secondary_section。进度合同为原始提取／路由 0～45、页理解 45～70、单元综合 70～80、规划 80～85、连贯整理 85～90、概览 90～94、内容 94～97、问题 97～99；成功发布才报 100。本轮定义账本与区间，不替换当前协调器的旧进度或虚构实际调用统计。

- demo 需要完整成功覆盖、Ready 综合、每个叶子都有选择依据来源、仅运行效果、没有教学目标和已观察操作；原始 operation 事实存在时也不能声明 demo。不能凭 IDE、录屏、无语音或能力缺失决定 demo。模式请求失败、无可用证据或全片输入超限时保守继承主类型，保存 fallback 与诊断，不把判断失败伪装成确认。
- 原始 ASR 候选从源段起止裁定到实际单元和视频范围；帧候选使用 metadata.pts_ms，并核对原始 startMs，播放区间最长 3000ms。其他有合法范围的原始文本证据只提供单元范围、precision=unit 的粗定位。没有可信范围就不生成候选，不由模型补时间。
- 锚点 ID 由当前 buildId 与确定顺序生成，引用只来自 Ready 页来源。模型只选择候选 ID；新增 entry.anchorPointIndex（JSON anchor_point_index）明确所选主要要点，验证锚点来源属于该要点、单元属于条目。无入口时 anchorId 为空、序号为 -1。全部候选只在任务中用于请求，presentation.anchors 仅保存已选入口，避免重复持久化未使用候选。

### 11.2 独立区域、长输入与来源合同

- primary_section 使用所有主类型与 demo 的既有受控策略，区域 kind／标题由程序赋值，模型不能自造标题策略。条目 kind、point role、question intent 与 attributes 通过白名单复核；entryId／questionId 必须来自程序为当前窗口提供的槽位，不接受任意 ID。
- 输入为完整单元综合、原始事实、综合要点、理解缺口、全片提纲及与当前窗口对应的锚点。每条至少一个有来源要点，条目 source_chunk_ids 恰好等于 points 的来源并集；只允许关联单元的成功理解来源，每个关联单元须有引用依据，拒绝失败页／未知／不相关来源和内部 ID 正文泄漏。
- step／operation 需要原始 operation 事实，并校验操作要点的来源；不能仅依据运行状态或综合背景写已观察操作。secondary_section 生成具体问题和受控 intent，问题前提须有成功理解来源；关联第一块条目时必须共享实际来源和单元，未知关联拒绝。Prompt 要求自测由视频可答，内容准确性仍需真实样本验证。
- 会议 action_item 只能在受控第二块生成，必须有原始 action_item 事实及有对应来源的 action 要点。未知 owner／deadline 规范为空字符串；非空值须同时对应同一条所引任务事实，拒绝把不同任务的责任人和期限拼在一起。待办只作视频展示，不调用外部任务工具，也不额外生成事实索引。
- 两块各自按完整单元窗口装入请求预算。短输入各请求一次，长输入分窗；每窗目标数量为上限，不设最低数量，不按字符切片或省略事实挤预算。单个单元、完整提纲、候选锚点或关联条目上下文仍无法容纳时，该窗口明确失败并继续处理后续窗口；已成功窗口和另一区域保持。
- 第二块完成后，对已经校验的问题按原文本比较去重，再从按窗口顺序排列的全片不同范围精选，优先不同 intent，默认最多 3 个。只选择原有问题，保留 questionId、原文、关联与引用，不为凑数填占位问题；会议真实待办不参与这个问题数量限制。
- 有证据但无可支持输出时，模型必须返回受控 skipped_reason；全部合法空输出为 Skipped，完全没有可用理解或没有成功窗口为 Failed，有内容但窗口失败／理解缺口为 Partial，其余为 Ready。第一块失败不阻止第二块独立生成有事实依据的问题；第二块失败不重试或清空第一块。
